# OrangeFox malachite device tree — review

- **Tree:** https://github.com/VikrieGunawan/orangefox-malachite at commit `b54f826` (merge of PR #1 "malachite-fixes", 2026-11-16)
- **Device:** Redmi Note 14 Pro 5G, `malachite`, MediaTek MT6878. It has dynamic partitions and virtual A/B. It uses FBE with metadata encryption.
- **Method:** Read-only review with no device available. The tree was compared against:
  - stock HyperOS OS2.0.206/208 global `vendor_boot.img` and `MT6878_Android_scatter.txt`
  - a LineageOS 23.2 `vendor_boot.img`
  - the stock 208 vendor partition
  - the crDroid 17.0 malachite device tree
  - a sysfs inventory taken on a tester's phone
- **Date:** 2026-11-16

## Verdict: not ready for a final release

| Severity | Count | Main risk |
|---|---|---|
| Critical | 4 | /data not decryptable, hard-brick path, unbootable image in CI artifacts |
| High | 5 | wrong /metadata filesystem, bootloader restore entries, unauditable root binaries, no touch |
| Medium | 6 | key upgrade risk, dim screen, wrong temperature, broken haptics |
| Low | 10 | stale values and leftovers |

Items marked **(verify)** could not be confirmed without a build output or a phone.

---

## Critical

### C1. /data encryption policy only matches HyperOS
- **Where:** `recovery/root/system/etc/recovery.fstab:20` and `recovery/root/system/etc/twrp.flags:3` set `fileencryption=aes-256-xts:aes-256-cts:v2+inlinecrypt_optimized`. `system.prop:7` sets `ro.crypto.volume.filenames_mode=aes-256-cts`.
- **Problem:** Stock HyperOS uses that value. AOSP-based malachite ROMs (crDroid, LineageOS and the other community trees) use `fileencryption=:aes-256-hctr2:inlinecrypt_optimized`, which means HCTR2 filename encryption. The recovery's vold reads the policy from `/etc/recovery.fstab`. On those ROMs the policy check on user 0 fails, so /data stays encrypted.
- **Fix:** Pick the policy at runtime from the slot's `/vendor/etc/fstab.mt6878`, or publish a HyperOS build and an AOSP build. The AOSP value is `aes-256-xts:aes-256-hctr2:v2+inlinecrypt_optimized`.

### C2. KeyMint and Gatekeeper HAL dependencies are not shipped (verify)
- **Where:** `recovery/root/vendor/bin/hw/android.hardware.security.keymint@3.0-service.mitee` and `android.hardware.gatekeeper-service.mitee`. Their NEEDED libraries are:
  - `android.hardware.security.keymint-V3-ndk`, `android.hardware.security.rkp-V3-ndk`
  - `android.hardware.security.secureclock-V1-ndk`, `android.hardware.security.sharedsecret-V1-ndk`
  - `libkeymint`, `lib_android_keymaster_keymint_utils`, `libkeymaster_messages`
  - `libcppbor_external`, `libcppcose_rkp`
  - `android.hardware.gatekeeper-V1-ndk`, `libgatekeeper`
- **Problem:** `recovery/root/vendor/lib64/` only has `libteecli.so` and `libtrusty.so`. The relink list at `BoardConfig.mk:162-164` only covers vibrator libraries. Stock keeps all of these in the vendor partition's `/vendor/lib64`, which is not what recovery sees. If the fox_16.0 build does not produce these exact versions, KeyMint fails to start. Then FBE and metadata decryption fail on every ROM.
- **Check:** `ls out/target/product/malachite/recovery/root/{system,vendor}/lib64 | grep -E 'libkeymint|keymint-V3|rkp-V3|cppcose|keymaster_keymint_utils|gatekeeper-V1|libgatekeeper'`
- **Fix:** Copy the libraries from stock vendor into `recovery/root/vendor/lib64/`, or add them to `TW_RECOVERY_ADDITIONAL_RELINK_LIBRARY_FILES`.

### C3. Boot control HAL switches the UFS boot LUN (hard-brick path)
- **Where:** `bootctrl/BootControl.cpp:139` calls `SetBootRegionSlot()`. `bootctrl/boot_region_control.cpp:269-316` sends a `QUERY_ATTR_IDN_BOOT_LUN_EN` write. The HAL is installed by `device.mk:85-87` and started at `recovery/root/init.recovery.mt6878.rc:2`.
- **Problem:** Every set-active-slot call changes which preloader copy the boot ROM loads. That includes the call update_engine makes when a ROM zip is flashed. AOSP ROM zips do not carry a preloader, and AOSP boot HALs never touch the boot LUN. If the other preloader copy is stale, the phone only reaches BROM mode.
- **Fix:** Use the AOSP boot control HAL for recovery, or remove the `SetBootRegionSlot()` call.

### C4. CI publishes a full `vendor_boot.img` that cannot boot (verify)
- **Where:** `.github/workflows/build.yml`, step "Collect build outputs". `BoardConfig.mk:170` sets `BOARD_INCLUDE_RECOVERY_RAMDISK_IN_VENDOR_BOOT`.
- **Problem:** Stock and LineageOS `vendor_boot` images contain two ramdisk fragments, a platform one and `recovery`. The stock platform fragment holds 223 kernel modules (LineageOS: 226), including UFS and display drivers (`ufs-mediatek-mod`, `phy-mtk-ufs`, `mediatek-drm`). This tree adds no vendor ramdisk content, so the built image's platform fragment has no modules. If someone flashes it with `fastboot flash vendor_boot`, neither Android nor the recovery can start. Fastboot itself still works, so this can be recovered.
- **Fix:** Publish only the installer zip, which replaces just the `recovery` fragment. Leave `FOX_VENDOR_BOOT_RECOVERY_FULL_REFLASH` unset. Check that `FOX_INSTALLER_VENDOR_BOOT_RAMDISK_INSTALL` is a real fox_16.0 variable.

## High

### H1. /metadata has the wrong filesystem
- **Where:** `recovery.fstab:19` and `twrp.flags:2` declare ext4. The partition is f2fs in stock, in AOSP trees, and in this tree's own `first_stage_ramdisk/fstab.mt6878:45`.
- **Problem:** The entry has the `formattable` flag, so a GUI format turns /metadata into ext4. First-stage mount then fails on the next boot.
- **Fix:** Use `f2fs` in both files.

### H2. Bootloader partitions can be backed up and restored
- **Where:** `twrp.flags`: `/lk` (43), `/preloader_raw` (50), `/tee` (55), `/gz` (42) and the other firmware entries at lines 33-56 all have `backup=1`. `/super` (11) is backed up as a raw image.
- **Problem:** Restoring an older preloader, lk or tee trips anti-rollback and hard-bricks the phone. Restoring a raw super image overwrites both slots and any virtual A/B snapshot.
- **Fix:** Remove the preloader_raw, lk, tee and gz entries. Make super backup-only, or remove it.

### H3. Root helper binaries hide their commands
- **Where:** `recovery/root/system/bin/mitee_helper` and `recovery/root/system/bin/vendor_watchdog`. Their strings are XOR-encoded with the key `0xA7`.
- **What they do once decoded:**
  - `mitee_helper` waits for `/mnt/vendor/persist` to be mounted, then runs `start vendor.keymint-mitee tee-supplicant vendor.gatekeeper-1-0 vendor.gatekeeper_mitee`.
  - `vendor_watchdog` waits for `/vendor`, then runs `setprop sys.vendor.watchdog ready`.
- **Problem:** Their behavior is harmless today, but closed root binaries with hidden strings cannot be audited. They are also the only thing that starts KeyMint, because every HAL `.rc` file uses `class none` and nothing else starts them. If persist fails to mount, decryption silently never starts.
- **Fix:** Replace both binaries with plain init triggers.

### H4. Touch drivers are not loaded (verify)
- **Where:** `BoardConfig.mk:158` sets `TW_LOAD_VENDOR_MODULES` to `haptic.ko flashlight.ko flashlights-led191.ko lm3644.ko`.
- **Problem:** The touch drivers (`ft3683g.ko`, `gt9916r.ko`, `xiaomi_touch_common.ko`) are in `vendor_dlkm`. They are not in the stock platform ramdisk. The tree ships touch firmware but never loads a touch driver.
- **Fix:** Add the three modules to the list.

## Medium

| # | Where | Problem | Fix |
|---|---|---|---|
| M1 | `BoardConfig.mk:44-48` | Version 99.87.36 and patch 2099-12-31 make KeyMint see a newer OS. If the recovery's vold saves upgraded key blobs, Android can no longer use them **(verify)**. | Make sure vold does not save upgraded keys. |
| M2 | `init.recovery.mt6878.rc:4-5` | UFS boot LUs `sda`/`sdb` are symlinked as `mmcblk0boot0/1`. Any script that writes the eMMC boot partitions overwrites the preloader. | Remove the symlinks. |
| M3 | `BoardConfig.mk:122-123` | `lcd-backlight` max_brightness is 20479, but the tree sets max 2047 and default 200, so the screen is very dim **(verify)**. | Raise the max to 20479 and scale the default. |
| M4 | `BoardConfig.mk:166` | `thermal_zone7` is the battery zone, not CPU. | Use `soc-top1` (zone 23) or a `cpu-*` zone. |
| M5 | `BoardConfig.mk:162-164`, vibrator service | The service needs `android.hardware.vibrator-V1-ndk`, but V2 is relinked. It dlopens libraries from `/odm/lib64`, which is not mounted. Haptics patch 0001 is optional in CI; without it, `vibrate()` blocks on `getService`. | Ship the V1 libraries, fix the paths, and make the patch mandatory. |
| M6 | `recovery/root/first_stage_ramdisk/fstab.{mt6878,emmc}` | Copies of the stock first-stage fstab go into the recovery fragment and overwrite the platform copy at the same path. AOSP ROMs read a higher-priority path, so this is fragile rather than broken **(verify)**. | Remove both files. |

## Low

- `BoardConfig.mk:65`: `BOARD_DTB_SIZE := 444463`, but `prebuilt/dtb` is 395011 bytes. The dtb is also not the 206/208 one (those are 394884 bytes and identical); it adds a `xiaomi,xm-chg-dfs` node from a newer firmware.
- `BoardConfig.mk:87`: `BOARD_MAIN_SIZE` equals the whole super partition; virtual A/B needs headroom. This does not affect a recovery-only build.
- `device.mk:98-101` and the CI variable `OF_DEFAULT_KEYMASTER_VERSION=4.1` refer to HIDL keymaster. The device uses KeyMint v3.
- `device.mk:6` uses `core_64_bit_only`, but `BoardConfig.mk:11-16` defines a 32-bit second arch.
- `BoardConfig.mk:136`: `TW_INPUT_BLACKLIST := "hbtp_vm"` is a Qualcomm leftover.
- `twrp.flags`: `audio_dsp`, `mvpu_algo` and `cust` do not exist on malachite. The first-stage fstab also lists partitions that do not exist (`lk1`, `bootloader2`, `tee1/2`, `scp1/2`, `md1dsp`, …).
- `twrp.flags:58`: `/usb_otg` is hardcoded to `/dev/block/sdd1` with `wipeingui`. That is only safe while UFS exposes 3 LUs **(verify)**.
- `recovery.fstab:2-17`: every logical partition appears twice (erofs and ext4), so the GUI may show duplicates.
- `init/init_malachite.cpp`: it forces the China model `24090RA29C` and a fixed `ro.build.date.utc=1756453697` (2025-08-29). `update_engine_sideload` refuses payloads older than that date.
- `BoardConfig.mk:68-72`: the permissive option writes `androidboot.selinux=permissive` into the vendor_boot cmdline.

## Checked and correct

- Boot header geometry matches stock:
  - base `0x3FFF8000`, kernel `0x40000000`, ramdisk `0x66F00000`, tags/dtb `0x47C80000`
  - header 2128, page 4096, cmdline `bootopt=64S3,32N2,64N2`
- Sizes match the scatter file: super 9663676416, vendor_boot 64 MiB.
- USB controller `11201000.usb0` matches stock.
- The screen is 1220x2712 and uses the `portrait_hdpi` theme.
- TEE device permissions and the TA path `/vendor/mitee/ta` match what `tee-supplicant` searches.
- The VINTF manifests match the shipped HALs.
- The metadata encryption key directory is correct.

## Top 3 must-fix before release

1. **Make decryption work:** ship the KeyMint/Gatekeeper libraries (C2), start the HALs from plain init scripts (H3), and set /metadata to f2fs (H1).
2. **Match the /data encryption policy to the ROM (C1):** HCTR2 for AOSP-based ROMs.
3. **Remove the brick paths:** the boot-LUN switch (C3), the preloader/lk/tee/super restore entries (H2), and the raw `vendor_boot.img` artifact (C4).
